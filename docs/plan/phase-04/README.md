## 阶段定位

为 StudyOS 建立可靠的关系型持久化。Phase 1 就刻意分组的知识模型（内容 / 状态 / 关系 / 学习数据）在本阶段落成表结构，知识层级与三种关系得到约束保证。

## 前置条件

- Phase 3 后端原型可用，存储模块边界清晰。
- 开发者理解 API 契约与后端分层；SQL 基础在本阶段边用边学。

## 目标矩阵

| 维度 | 内容 |
| --- | --- |
| 产品目标 | 知识、关系、任务、记录可靠持久化，重启不丢、关系可查询 |
| 用户价值 | 数据真正属于自己的学习系统，可长期积累 |
| 技术目标 | 关系模型与 SQL、主键 / 外键 / 约束、查询 / 筛选 / 排序 / 分页 / 关联、PostgreSQL、ORM 模型映射、迁移、事务与索引意识 |
| 学习目标 | 见 [学习路线#Phase 4](../learning-roadmap.md) |
| 实践方式 | 先画 ER 模型再建表；用迁移脚本演进；临时存储整体替换为 ORM repository |
| 验证方式 | 数据重启后存在且关系正确；能解释每条约束防住了什么错误 |
| 阶段产出 | 模型明确、可迁移、带基础约束与索引的后端数据层 |

## 功能范围

**做什么**：

- 核心表（最终形状进入阶段时确定，规划方向）：知识节点表、知识内容表、用户状态字段组、关系表（type: related / prerequisite，parent 用节点上的 parent_id）、任务表、学习记录表；
- 层级查询（某领域子树）、关系查询（相关 / 前置知识）、按知识聚合任务与记录；
- 外键约束与删除规则（删除知识时任务 / 记录 / 关系如何处理，必须显式决策，不允许悬空数据）；
- 迁移脚本与初始化数据；掌握度变化历史以 learning_records 为准，不覆盖历史。

**不做什么**：缓存、读写分离、分布式数据库、微服务、图数据库、多态自定义关系（留 Horizon）、复杂报表。

## 架构要点

- 内容与状态在关系层面分开：节点主表 + 内容表 + 状态字段组，使 P6 按用户隔离、P9 向量化内容时改动最小。
- 关系表带方向：related 语义对称（查询时双向展开），prerequisite 有方向。
- 所有表先不带 user 概念（P6 统一加 owner），但表结构设计时预留归属列位置意识。
- ORM 模型与 API 契约分离：不把 ORM 对象裸返回给前端。
- 本地开发数据库连接信息走环境变量，提交中不含密码。

## 验证标准

- **功能验收**：核心数据重启后完整存在，增删改查与关系查询正确。
- **技术验收**：表结构、外键、约束、索引、迁移脚本合理；典型查询的 N+1 问题有意识并能说明取舍。
- **知识验收**：能解释 SQL 与 ORM 的关系、事务的意义、约束如何保证一致性、数据库与 localStorage 的本质区别。
- **工程验收**：模型可演进（迁移而非手动改库）、配置不硬编码、边界错误可追踪。

## 主要风险

- 表结构照 API 响应画，导致内容 / 状态混在一起——回到 [Phase 1 数据模型](../phase-01/README.md#数据模型规划级不是代码) 四组分组核对。
- 删除规则含糊产生孤儿数据——删除策略必须显式写进计划与测试。
- 过度设计索引 / 分表——当前数据量下明确禁止。
