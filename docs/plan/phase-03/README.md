## 阶段定位

建立 StudyOS 的第一个后端服务，理解浏览器、HTTP、API、服务器之间的数据流。知识 / 任务 / 记录从“浏览器本地数据”变为“通过契约访问的资源”。本阶段**先不接数据库**，服务端使用临时存储，专注协议与边界。

## 前置条件

- Phase 2 完成：前端有清晰的 repository 接缝，可将存储实现从本地替换为 HTTP。
- 开发者理解 JSON、异步编程（P2 实践中已接触）与基础 Python 语法（进入阶段时按需补）。

## 功能范围

**做什么**：

- 资源 API：knowledge nodes（含层级）、relations、tasks、learning records；
- 规则建议可先留在前端，也可提供 `recommendations` 只读端点（进入阶段时按学习负担二选一，记录决策）；
- 请求参数与 body 校验、404 / 400 / 422 等错误的统一返回格式；
- 前端 repository 从 localStorage 实现切换为 HTTP 实现；
- 加载态与请求失败的基础用户反馈。

**不做什么**：数据库与 ORM（P4）、认证鉴权（P6）、部署（P12）、异步任务队列、微服务、缓存层、自动生成的庞杂 API。

## 架构要点

- REST 资源命名与前端模型一致：`/knowledge-nodes`、`/relations`、`/tasks`、`/learning-records`。
- 临时存储模块单独封装，接口形状向未来的数据库 repository 对齐，P4 只替换内部实现。
- 内容 / 状态分组在 API 契约中保持可见（响应结构体现分组），为 P4 拆表做准备。
- 配置通过环境变量注入；不硬编码端口 / 来源 / 未来密钥。

## 验证标准

- **功能验收**：前端通过 API 完成知识、任务、记录的核心读写流程。
- **技术验收**：方法与状态码使用正确；校验错误、未找到、非法 JSON 都有明确响应；CORS 配置可用且不泄露敏感配置。
- **知识验收**：能讲清一次请求从浏览器到路由处理再返回的全过程、REST 资源思想、前后端职责边界。
- **工程验收**：API 命名与职责一致，错误不被静默吞掉；契约有文档（接口表或自动文档），前端能据此对接。

## 主要风险

- 一上来就接数据库导致同时学三样东西——严格使用临时存储。
- API 形状随写随改、前后端互相看不懂——契约先行并文档化。
- 把业务规则散落在路由函数里——校验 / 业务 / 存储分层，哪怕每层很薄。
