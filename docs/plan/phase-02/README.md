## 阶段定位

把 Phase 1 的原生 JavaScript MVP 演进为组件化、类型清晰、可持续扩展的前端应用。**产品闭环不新增重大能力，重点是工程形态升级**；这是“先理解本质，再使用框架”原则的落点。

## 前置条件

- Phase 1 闭环完整跑通并有清晰 Git 历史。
- 开发者已能手写 DOM 更新、事件处理与 localStorage 数据层，理解命令式 UI 的痛点（这是本阶段学习动机的来源）。

## 目标矩阵

| 维度 | 内容 |
| --- | --- |
| 产品目标 | 知识树、知识详情、关联任务、学习记录、规则建议在组件化前端中体验一致、可维护 |
| 用户价值 | 界面响应更稳定、交互反馈更完整，数据不易出现 UI 与状态不一致 |
| 技术目标 | React 组件 / props / state、表单与条件渲染、组件组合与单向数据流；TypeScript 类型 / interface / 泛型基础；Vite 与 npm 构建流程 |

| 验证方式 | P1 端到端走查场景在新前端全部通过；能解释每个组件的数据来源 |
| 阶段产出 | 组件化、类型化、通过 Vite 构建运行的 StudyOS 前端 |

## 功能范围

**做什么**：

- 用组件重建知识总览、知识详情、任务与记录、建议区；
- 抽取可复用单元：知识树节点、掌握度控件、标记重点、任务项、记录条目、建议卡片、表单；
- 用 TypeScript 类型定义 KnowledgeNode / Task / LearningRecord / Recommendation（直接承接 P1 数据模型，类型即文档）；
- 数据访问收敛到 repository / store 模块，组件不直接碰 localStorage——为 P3 替换为 HTTP 客户端预留接缝；
- 保持本地持久化与 P1 全部能力。

**不做什么**：后端、数据库、复杂状态管理库（Redux / Zustand 等除非真实复杂度证明必要）、前端路由库（视图简单时用条件渲染即可）、UI 组件库、微前端、为抽象而抽象的设计模式。

## 架构要点

- 目录按功能 / 组件职责划分；类型定义集中管理。
- 存储层接口在本阶段定型：`knowledgeRepository.list/get/save/delete` 这样的职责边界，P3 只替换实现。
- 规则建议引擎保持为纯函数模块，可用 TypeScript 为输入输出加类型。
- 本地数据从 P1 迁移：读取旧 schema 版本并做一次兼容处理（第一次真实的数据迁移练习）。

## 验证标准

- **功能验收**：P1 闭环走查 9 步在新前端中全部通过。
- **技术验收**：组件职责单一、状态归属合理、key 与列表正确、无直接 DOM 操作；`tsc` 与构建无错误。
- **知识验收**：能解释声明式 vs 命令式、受控组件、单向数据流、类型系统拦截了哪类错误。
- **工程验收**：模块划分可通读，构建 / 开发命令稳定，无无理由的复杂抽象与冗余依赖。

## 主要风险

- 照着教程抄组件但不理解状态归属——通过 Review 门中“指出每个 state 为什么在这里”防范。
- 借重构之名加新功能导致范围蔓延——本阶段功能范围与 P1 严格对齐。
- 过早引入状态库 / 路由库——列为明确禁止项。
