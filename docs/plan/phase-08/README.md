## 阶段定位

在真实学习数据（知识、记录、测评、掌握度）之上引入大语言模型，构建**可解释、可控制**的 AI 智能层。AI 是跨系统的 Advisor，不是孤立页面，更不是 Controller：所有输出以**提案**形式呈现，用户接受 / 修改 / 拒绝后才生效。Phase 1 的规则建议引擎在本阶段被 AI 增强（规则仍保留为兜底）。

## 前置条件

- Phase 7 提供结构化掌握度信号；学习记录与知识内容有足够积累（没有数据的 AI 分析是空谈）。
- 全栈与认证稳定：密钥可安全存放于服务端，AI 请求以当前用户数据为边界。
- 开发者已理解后端服务、配置管理与错误处理。

## 目标矩阵

| 维度 | 内容 |
| --- | --- |
| 产品目标 | AI 分析薄弱点、解释掌握度变化、生成下一步建议与理由、辅助整理知识结构与关系、出题、复盘；建议全部提案化 |
| 用户价值 | 得到“基于我的真实学习数据、且讲得清为什么”的指导，同时保留全部决定权 |
| 技术目标 | LLM API 交互、Prompt 与上下文组织、结构化输出与校验、重试 / 超时 / 速率限制 / 成本控制、隐私边界、幻觉认知与效果评估 |
| 学习目标 | 见 [学习路线#Phase 8](../learning-roadmap.md) |
| 实践方式 | 先做一个最有价值的场景（薄弱点分析 + 建议理由）跑通 AI 服务层，再逐场景扩展 |
| 验证方式 | AI 建议可追溯到具体数据；失败可降级到规则引擎；用户可拒绝且系统行为正确 |
| 阶段产出 | 与业务解耦的 AI 建议层 + 提案交互（接受 / 修改 / 拒绝） |

## 功能范围

**做什么**（按价值排序，进入阶段时裁剪）：

- 薄弱点分析与下一步建议（增强 P1 规则引擎，附数据依据）；
- 解释掌握度变化（引用学习记录与测评结果）；
- 辅助生成 / 整理知识：补全定义草稿、建议 related / prerequisite 关系（用户确认后落库）；
- 根据知识生成练习题（客观题先进入 P7 题库流程，不直接生效）；
- 阶段复盘：汇总一段时间的学习记录。

**不做什么**：RAG / 个人知识库检索（P9）、Agent 工具调用与自动执行（P10）、无确认写操作、AI 自动判分的主观题（先人工确认）、多模型编排、公开分享 AI 生成内容。

## 架构要点

- AI 能力集中在独立服务模块（后端），业务模块通过明确接口调用；密钥只在服务端。
- **提案模型**：AI 输出统一为 proposal 结构（类型、内容、依据、置信度），持久化后由用户决策；不允许 AI 直接改业务表。
- 结构化输出必须校验，校验失败走重试 / 规则兜底 / 明确报错，不把脏数据当建议展示。
- 上下文最小化：只发送当前建议所需的用户数据，遵守 P6 的数据边界；记录调用行为与成本。
- 规则引擎保留：AI 不可用、超时、超预算时，系统退回 P1/P7 的规则建议，闭环不停转。

## 验证标准

- **功能验收**：至少一个分析场景端到端可用；每条建议能展示依据；接受 / 修改 / 拒绝三条路径行为正确。
- **技术验收**：超时、重试、限流、非法输出、空数据上下文均有处理；密钥不泄露；成本可观测。
- **知识验收**：能讲清 Prompt 与上下文如何影响结果、幻觉从何而来、为什么需要结构化校验与降级。
- **工程验收**：AI 模块与核心业务解耦、可替换供应商；调用与提案决策可追踪。

## 主要风险

- AI for AI's sake：没有数据就接模型——前置条件不满足不启动。
- 用户盲信建议——强制展示依据与置信度，关键变更必须确认。
- 成本与超时失控——限流、预算与降级在第一个场景就建立。
- 让 AI 直接写库——提案模型是硬性架构约束。
