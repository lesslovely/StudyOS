## 阶段定位

把 StudyOS 封装为一致、可重复的运行环境，并部署到真实服务器，完成从“本地能跑”到“线上可用、可更新、可诊断”的软件交付闭环。容器化与部署对单人学习项目是一条连续链路，因此合并为一个阶段，内部分两个里程碑。Phase 12 不是终点：真实运行会继续暴露性能、可靠性、安全与架构问题，之后按需求驱动进入 Horizon。

## 前置条件

- Phase 11 质量体系就位，发布前有自动化验证把关。
- 应用组件（前端、后端、数据库、向量库等）齐备，本地多服务启动已显繁琐——这是容器化的真实动机。

## 里程碑 A：容器化（对应旧 Docker 阶段）

- 为前端、后端、数据库（及向量库，如已引入）编写镜像与 Compose 编排；
- 数据卷持久化明确；服务间网络与启动顺序正确；
- 环境变量与密钥通过配置注入，镜像与仓库中不含敏感信息；
- 一条命令在新机器上拉起完整开发 / 运行环境。
- **不做**：Kubernetes、镜像仓库高级流水线、多环境集群。

## 里程碑 B：生产部署（对应旧 Linux 部署阶段）

- 云主机初始化：Linux 用户、权限、防火墙、基础安全；
- Nginx 反向代理后端、托管前端静态资源；域名与 DNS；HTTPS 证书与续期；
- 容器在主机上稳定运行（重启策略）；日志收集与查看；
- 数据库定期备份与恢复演练；基础监控（进程 / 端口 / 磁盘）与告警（最简形态）；
- 发布流程文档化：更新 → 验证 → 发布；出问题如何回滚；
- AI 密钥、数据库密码等通过主机环境安全管理。

## 验证标准

- **功能验收**：通过 HTTPS 域名可完成核心学习闭环；发布与回滚流程各实际执行至少一次。
- **技术验收**：容器构建 / 网络 / 卷 / 依赖顺序正确；Nginx、证书、备份配置实际生效。
- **知识验收**：能讲清请求从域名 → DNS → Nginx → 前端 / 后端 → 数据库的完整路径，并能定位常见故障。
- **工程验收**：从零部署步骤可复现；敏感信息受保护；有日志、备份、监控与回滚的最小实践；记录运行成本与维护责任。

## 主要风险

- 没有真实发布需求就为学 Docker 而容器化——以前置条件（多服务启动繁琐）为启动信号。
- 密钥进镜像 / 进仓库——配置审计列为硬性检查。
- 只部署不验证恢复——备份必须做恢复演练，回滚必须实际走一遍。
- 一次性引入 K8s 等复杂平台——明确禁止。
