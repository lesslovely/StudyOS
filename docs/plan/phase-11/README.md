## 阶段定位

当 StudyOS 同时包含前端、后端、数据库、测评、AI、RAG 与 Agent 时，仅靠手动验证无法可靠发现回归。本阶段把此前各阶段零散的验证习惯**体系化**：建立与系统规模匹配的测试金字塔、静态检查与 Git 工作流，让后续迭代敢改、改得动。

> 注意：本阶段不是“才开始测试”。Git 提交习惯与手动验证从 [Phase 1](../phase-01/README.md) 起步，store / rules 等纯函数从 P1 起就按可测方式组织；本阶段是补齐自动化与工程体系。

## 前置条件

- Phase 10 完成，系统复杂度足以暴露“没有自动化测试就不敢改”的真实痛点（这是本阶段的学习动机）。
- 各模块职责边界清晰，存在可独立测试的纯函数与 API。

## 功能范围（工程能力）

**做什么**：

- 单元测试：规则建议引擎、掌握度聚合、组卷评分、数据校验等纯函数；
- API / 集成测试：知识 / 任务 / 记录核心流程、认证与归属隔离、错误路径；
- 前端测试：关键组件渲染与交互（如完成任务 → 记录出现 → 掌握度变化）；
- 少量高价值端到端测试：覆盖 P1 定义的端到端闭环走查；
- AI 相关测试策略：不依赖真实模型调用（替身 + 固定响应），重点测提案流程、校验、降级与确认门；
- 静态检查、格式化、统一的一键验证脚本；
- Git 工作流：分支用途、提交信息约定、合并前自查 / Review 清单。

**不做什么**：为覆盖率数字写无价值测试、复杂 CI 平台建设、追求 100% 覆盖、性能压测体系（留到真实需要时）、自建测试框架。

## 架构要点

- 测试金字塔：大量纯函数单测，适量集成 / API 测试，少量高价值 E2E。
- AI 与外部服务必须可替换：测试通过替身控制返回，验证业务逻辑而非模型效果。
- 安全相关路径（越权访问、Agent 未确认写操作）必须有自动化负向测试。
- 验证命令统一、文档化，进入每个后续 Phase 的完成定义（Definition of Done）。

## 验证标准

- **功能验收**：核心流程与关键失败场景有可重复的自动验证方式。
- **技术验收**：测试层次合理、结果可信、能稳定复现；静态检查能发现常见问题。
- **知识验收**：能说明各类测试的目的、边界、取舍，以及为什么不该追求覆盖率数字。
- **工程验收**：提交表达清晰、Review 有清单、回归可定位；一键验证可在新环境跑通。

## 主要风险

- 为覆盖率补测试——以风险与回归价值排序。
- 测试依赖真实 AI / 网络导致不稳定——替身与固定夹具（fixture）。
- 只测 happy path——认证越权、AI 降级、Agent 确认门等负向路径是重点。
