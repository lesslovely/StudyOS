## 阶段定位

“感觉学会了”不可靠。本阶段为 StudyOS 建立结构化测评能力：围绕单个知识与关联知识组合作答，系统据此更新掌握度，让掌握度从 Phase 1 的单一自评信号升级为**自评 + 测评结果的规则聚合**。本阶段不使用 AI 判题，先把测评建模、组卷、评分与信号聚合做扎实——这也是 Phase 8 AI 建议质量的数据前提。

## 前置条件

- Phase 6 完成：测评数据按用户隔离。
- 知识关系数据已积累（prerequisite / related），综合测评才有“关联知识”可组卷。
- 学习记录链路稳定（测评结果同样走 Learning Record → Knowledge State Update）。

## 目标矩阵

| 维度 | 内容 |
| --- | --- |
| 产品目标 | 单知识测试；关联知识综合测试（如：闭包 → 函数 → 作用域 → 作用域链）；测评结果回写掌握度；薄弱点判断更可信 |
| 用户价值 | 用检验代替自我感觉；知道“哪里真的会、哪里只是眼熟” |
| 技术目标 | 题库 / 试卷 / 作答 / 评分的数据建模；组卷规则；评分与掌握度聚合规则；结果统计 |
| 学习目标 | 见 [学习路线#Phase 7](../learning-roadmap.md)；同时是开发者练习规则引擎与数据建模的载体 |
| 实践方式 | 先做单一题型单知识测试跑通链路，再扩展题型与综合组卷 |
| 验证方式 | 一次综合测评能正确评分、生成记录、改变掌握度并影响建议 |
| 阶段产出 | 测评子系统 + 多信号掌握度聚合规则 |

## 功能范围

**做什么**：

- 题目与知识节点关联（题目属于一个主知识，可标记涉及的关联知识）；
- 单知识测试：针对一个 Knowledge Node 组卷；
- 综合测试：沿 prerequisite / related 关系选择关联知识组卷（先用简单规则：前置 + 直接相关）；
- 题型按实现成本分两步：先客观题（选择 / 判断 / 填空，可规则判分）；再简答 / 代码题（本阶段仅支持人工自评或简单规则，AI 判题留待 P8 之后）；
- 测评结果：得分、逐题结果、掌握度建议变化值（规则给出，用户确认后生效——延续 Advisor 原则）；
- 测评行为写入 Learning Record；测评历史可查。

**不做什么**：AI 自动出题与判题（P8+）、编程题在线运行判题（Horizon）、间隔重复算法（Horizon）、竞争性排名、标准化考试式题库、复杂教育测量理论（IRT 等）。

## 掌握度聚合规则（规划方向）

- 掌握度仍为 1~100；本阶段建立可解释的简单聚合：自评与最近测评结果加权（测评权重随测评次数上升），具体权重进入阶段时与开发者共同确定并记录。
- 规则必须可解释：界面能说明“掌握度为何变化”（哪次测评、哪些题）。
- 单次低分不直接清零、单次高分不直接满级；变化幅度设上下限，避免抖动。
- 不对外宣称系统能精确测量能力（[D-007](../decisions.md)）。

## 架构要点

- 新增数据模型：questions、assessments（一次测评）、attempts（作答与得分）、mastery_events（掌握度变化事件，与学习记录互补）。
- 组卷与评分是独立纯规则模块，与 P1 规则建议引擎同级、同风格——它们在 P8 都是 AI 可增强 / 替换的接缝。
- 测评与学习闭环的接线：`Assessment → Attempt → 评分 → 掌握度变化提案 → 用户确认 → Learning Record / mastery event → 建议更新`。

## 验证标准

- **功能验收**：能对 `闭包` 发起单知识测试与一次关联综合测试；结果正确入库并改变掌握度与建议。
- **技术验收**：题目 / 测评 / 作答模型关系清晰；组卷规则可重复；评分边界（缺答、全错、重测）处理明确。
- **知识验收**：能讲清多信号聚合为何这样加权、为什么测评比自评权重高、规则引擎在何处为 AI 预留接缝。
- **工程验收**：测评数据按用户隔离；历史不被覆盖；聚合规则变更有记录。

## 主要风险

- 一上来追求多种题型导致烂尾——客观题先行，链路完整优先。
- 聚合公式过度复杂、不可解释——坚持简单可讲清。
- 测评结果直接静默改掌握度——必须经用户确认，守住 Advisor 边界。
