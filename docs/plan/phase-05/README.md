## 阶段定位

把前端、API、数据库连接成一个可持续真实使用的基础全栈应用，验证学习闭环在真实数据流（而非本地假数据）中完整成立。这是第一次端到端集成，重点是数据流与边界状态，不是新功能。

## 前置条件

- Phase 4 数据层可用，迁移脚本可重复执行。
- Phase 2 前端 repository 接缝仍清晰，未在组件中散落 fetch 调用。

## 目标矩阵

| 维度 | 内容 |
| --- | --- |
| 产品目标 | 知识闭环全部流程跑在服务端数据上；本地数据平稳迁移；跨页面状态一致 |
| 用户价值 | 可以长期、稳定地把学习数据积累在一个地方 |
| 技术目标 | API 客户端、异步状态、加载 / 空 / 错误三态、表单校验与数据转换、接口契约与版本意识、基础日志与问题定位 |
| 学习目标 | 见 [学习路线#Phase 5](../learning-roadmap.md) |
| 实践方式 | 以“完成任务 → 生成记录 → 掌握度更新”链路做端到端打通的样板，再推广到全部流程 |
| 验证方式 | 能独立追踪一次操作从 UI → API → 数据库 → 返回 → 重渲染的全过程 |
| 阶段产出 | 前后端分离、数据持久化、可长期使用的 StudyOS 基础版本 |

## 功能范围

**做什么**：

- 知识总览读取真实汇总数据（薄弱点、待办、最近记录由后端返回或由前端基于真实数据计算，进入阶段时定）；
- 知识、关系、任务、记录的完整增删改查走通三层；
- 本地 localStorage 数据一次性迁移到服务端（提供迁移路径与校验，迁移后本地数据如何处理需显式决策）；
- 加载态、空数据引导、请求失败反馈、表单前后端双重校验；
- 规则建议引擎与真实数据对接（仍为规则，不上 LLM）。

**不做什么**：微服务、复杂缓存、复杂状态框架、实时推送、AI 能力、认证（下一阶段）。

## 架构要点

- 前端错误不吞、后端错误有统一格式与日志；问题能定位到具体层次。
- 契约变更走显式沟通：本阶段前后端都由开发者一人承担，仍要求先改契约文档再改实现，养成习惯。
- 关键写操作（完成任务、改掌握度）保持在后端同一事务 / 同一业务流程中生成关联记录，避免数据不一致。

## 验证标准

- **功能验收**：P1 端到端闭环走查在全栈版本中全部通过；刷新 / 重开后状态一致。
- **技术验收**：异步请求、三态处理、数据校验、边界输入合理；无静默失败。
- **知识验收**：能画出一次写操作穿越三层的时序，并指出每层职责。
- **工程验收**：前后端职责清晰、契约有据可查、本地迁移可重复执行且结果可核对。

## 主要风险

- 集成期同时暴露前后端问题导致混乱——按一条链路打通再横向推广。
- 迁移脚本写丢本地数据——迁移前导出备份并校验条数。
- 错误处理只做 happy path——三态与失败路径列入验收硬指标。
